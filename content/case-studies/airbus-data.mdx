> **TL;DR**  
> Durante mis prácticas en Airbus trabajé en un caso de **data analytics orientado a la toma de decisiones de ingeniería**: estimar impacto de cambios (especialmente **reducción de peso**) a partir de **estructuras de producto (BOM)** del **A320** (componentes del **HTP/VTP**) filtradas por **Manufacturing Serial Number (MSN)** o por **aplicabilidad/configuración**.  
> El resultado fue un **dashboard** (listo para pilotaje) apoyado por un **pipeline** (PySpark/SQL) que permitía consultar estructura de producto, contar instancias de estándares y calcular **peso total** y **delta de peso** en escenarios “antes/después” al sustituir estándares (tornillos/tuercas/etc.).

## 1) Contexto y objetivo
### Problema
En ingeniería/diseño, para campañas de mejora (p.ej. reducción de peso) o decisiones de mantenimiento/reparación, es clave responder rápido a preguntas como:
- “Si sustituyo este estándar por otro más ligero, ¿cuántas instancias afecta según la aplicabilidad/MSN?”
- “¿Qué peso total representa este estándar dentro del HTP/VTP en una configuración concreta?”
- “¿En qué subassembly aparece y cuántas veces?”

### Objetivo del proyecto
Construir un producto de datos (pipeline + dashboard) que habilitase **trade-off analysis**:
1) Filtrar por **MSN** (avión concreto) o por **configuración/aplicabilidad** (rango de MSNs que comparten una configuración).
2) Extraer la **BOM** del HTP/VTP y navegar por niveles (subassemblies → parts → standard parts).
3) Contar instancias de un **standard part** específico (por código).
4) Calcular **peso total** y **comparativas antes/después** ante sustituciones (standard A → standard B).

## 2) Datos: fuentes y modelo (sin detalles sensibles)
### Fuente principal (legacy PLM → banco de BBDD)
- Los datos provenían de un **PLM legacy** interno (histórico del A320).
- Airbus había generado un **banco de bases de datos** con información extraída/recreada a partir de ese sistema legacy.
- El proyecto usaba:
  - **estructuras de producto físicas (BOM)** del HTP/VTP,
  - relaciones padre-hijo para navegar assembly → subassembly → part → standard part,
  - información de aplicabilidad (MSN/configuración).

### Enriquecimiento: catálogo de estándares
- Se integraba con una tabla/catálogo de **standard parts** (por código) para obtener datos como:
  - material,
  - peso unitario (y otros metadatos útiles para trade-offs).

## 3) Solución: pipeline + dashboard
### Pipeline (transformaciones / joins)
- Implementación mediante una herramienta de pipelines estilo “bloques” (inputs/outputs), con transformaciones en **PySpark/SQL**.
- El pipeline:
  - filtraba por **MSN** o por **aplicabilidad/configuración**,
  - reconstruía la **estructura de producto** del HTP/VTP,
  - permitía agregaciones (conteos) y joins con catálogo de estándares (peso/material),
  - publicaba tablas/datasets listos para consumo del dashboard.

![Pipeline blocks](/media/case-studies/airbus-data/diagram-4-pipeline-blocks.svg)

### Dashboard (cara a usuario)
El dashboard (en el entorno de **Palantir / Skywise**) permitía:
- seleccionar **MSN** o **configuración/aplicabilidad**,
- visualizar la **BOM** del HTP/VTP (con navegación por niveles),
- buscar un **standard part** por código,
- ver:
  - número de instancias (conteo),
  - peso total asociado (instancias × peso unitario),
  - localización en la estructura (en qué subassembly aparece),
  - (cuando aplicaba) comparativa **antes/después** al sustituir A → B, mostrando **delta de peso**.

## 5) Deep dive (STAR) — Validación y detección de “missing data”
### S — Situation
Estábamos filtrando por **MSN** y reconstruyendo la **BOM del HTP/VTP** desde la base “recreada” para alimentar el dashboard y soportar cálculos de peso y conteos.

### T — Task
Validar que la estructura generada por la base recreada coincidía con la referencia legacy, para evitar que el análisis de trade-offs se basara en datos incompletos.

### A — Action
- Extraje la BOM del HTP/VTP filtrada por un MSN desde la base recreada.
- Consulté la herramienta legacy (fuente original) y exporté la estructura equivalente a CSV.
- Crucé ambos CSV con un script y generé un **informe de diferencias** (faltantes por tipo/código y cantidad).
- Escalé al equipo dueño del DB bank con informe + scripts para **reproducir** el caso.

### R — Result
Detectamos una discrepancia pequeña en volumen pero crítica para trade-offs:
- BOM total ~**1000** ítems (componentes + estándares),
- faltaban **~10–15** instancias, concentradas en un tipo de estándar (p.ej. un tornillo concreto),
- suficiente para sesgar **conteos** y **peso total** y, por tanto, decisiones de ingeniería.
