## TL;DR
In the **Eurodrone** program I spent ~2 years in **Configuration Management (CM)** in a highly rigorous environment. In parallel, I joined **One Platform** from day one as a “customer” role—Airbus’ transformation initiative where **3DEXPERIENCE** is the backbone for **PLM + Change Process + Configuration**. I translated high‑level processes (Change / Equipment Release) into implementable tool logic, validated releases with **end‑to‑end UAT** (including negative testing), and led much of the **training and adoption** in Getafe.

## Role & Scope
**Role:** Configuration Management Analyst (ALTEN, embedded at Airbus)  
**Location:** Getafe (Madrid)  
**Period:** 08/2023 – 09/2025  
**Personal scope:** Change Process + Configuration definition + Equipment Release / Teams management + UAT + Training/Adoption

## Context
**One Platform** is a group‑wide initiative to **unify, modernize, and improve** Airbus processes (commercial, helicopters, defense, space) with a view to future programs. Inside One Platform, **3DEXPERIENCE** acts as the backbone connecting lifecycle stages: **requirements → systems engineering → design → manufacturing → services**, plus **configuration management** and a rigorous **change process**.

## Deep dives

### Deep dive — Multi-view approach (Systems)
A key element was a **Multi‑View** methodology, where product evolution is governed through **coherent views** per discipline, keeping **traceability** and consistency via the change process.

**Main views (simplified)**
- **Requirements View:** system/subsystem tree for customer/internal/supplier requirements.
- **Logical / Functional View:** translate requirements into functions, logic, and relationships.
- **Equipment View:** map architecture to equipment and enable equipment release/supplier interface.
- **Technical View:** capture technical inputs (e.g., electrical connections) for design/verification.
- **Design View:** detailed product structure aligned with systems/equipment.
- **Service View:** downstream consumption (services/operations).

**How this connected to CM + Change**
- Configuration is defined “by views” (objects, baselines, versioning) and variants via applicability.
- The Change Process governs modifications across views.
- The key value was ensuring views could be **operated** in a PLM platform with rules, reviews, and traceability.

### Deep dive — Delivery flow (SAFe/UAT)
The project used **Scaled Agile / SAFe** at high level:

- **Epic** (e.g., Change Process)
- **Business Release**
- **Dossier** (use cases + requirements + acceptance criteria)
- Developer implementation
- **Test Campaign** (end‑to‑end UAT as customer)
- **Release** (continuous delivery)

Typical contributions:
- Translate real use cases into verifiable requirements.
- Align with functional architects to turn needs into implementable logic.
- Validate **end‑to‑end** (including bypass scenarios).
- Report defects/IRs and retest in following iterations.

**Artifacts produced/managed**
- Use cases + requirements (Confluence / dossier)
- Acceptance criteria + UAT checklist
- Bugs / improvement requests (Jira)
- Training materials (slides, guides, exercises)
- Live operational support

### Deep dive — Doc‑centric → Data‑centric
**Before (doc‑centric)**
- Change process dossiers in PowerPoint (SharePoint check‑in/check‑out).
- Duplicate information in Jira and PPT.
- Manual work and friction.

**After (data‑centric)**
- Deliverable = data + tool visualization.
- Integration with real 3DEXPERIENCE objects:
  - impact analysis tied to changing objects,
  - richer evidence (comments/markups),
  - less duplication and more traceability.

![Doc-centric → Data-centric](/media/case-studies/one-platform/diagram-3-doc-to-data.svg)

### Deep dive — Equipment Release hardening
**Goal:** ensure the Equipment Release Process can’t be “gamed.”

**What was implemented (summary)**
- Key object evolving through revisions.
- State progression.
- Release gate requiring mandatory attributes + correct state.

**My actions**
- Push to use OOTB capabilities + Airbus rules.
- Translate logic into dossiers (use cases + acceptance).
- Execute end‑to‑end UAT with negative testing mindset.

**Validation (how it was tested)**
- Create object → force incomplete scenarios → attempt release → verify block.
- Complete attributes → advance state → release → verify compliance.
- Try bypass → raise IR → retest after fix.

**Result**
- Hardened flow and better process rigor.
- In this slice: **~15–20** bugs/IRs found and resolved.
- Evolution across **~4–5 releases** (continuous development).

## Outcomes & Impact
- **End‑to‑end use** in MVP1 by design and systems teams.
- Resistance decreased after ~2 months as benefits became clear.

> Note: I left before full adoption could be confirmed, but clear signals of usage and reduced resistance were observed.

## Learnings
- **Real scale:** aerospace/defense programs are huge ecosystems; software/process must survive that complexity.
- **Human adoption:** the hard part isn’t the tool, it’s change.
- **Stakeholders everywhere:** map dependencies and align via workshops.
- **Customer‑side delivery:** use cases → acceptance → UAT E2E → bugs/IR → retest.
- **Doc → Data:** lived the shift from fragile documentation to data‑centric flows.

**What I’d do differently**
- Build stakeholder network earlier to speed decisions.
- More product‑like training for leaders (materials, FAQs, exercises).
- Internal communication campaign on “why” and “what each role gains.”

## Takeaways
1. Translate process → software: define needs and turn them into implementable requirements.
2. Real enablement: hands‑on training and operational support.
3. Experience in massive, complex programs (Eurodrone + One Platform).
